## Decision

### 1. The reversal

Claude Code Projects mode is **resumed** as the first target runtime for Conductor-governed
work. The owner's decision of 2026-10-22 11:07 UTC on #37 and #41, which parked Projects
and restored the standalone roles model, is **superseded** by the owner's confirmation of
2026-10-22 12:56 UTC in the project thread. The Projects-round answers of 10:21 UTC on #37
(Q1, Q3 and Q5, previously parked) are back in the Ready scope. Everything else decided on
#36 and #37 stands.

### 2. One vendor-neutral core in `shared/`

The core names no product. It is what every adapter is generated from and what every
runtime reads at a task boundary. It consists of:

- **Records.** The task issue with the Ready facts (outcome, acceptance criteria, non-goals,
  allowed paths, stop conditions); the pinned Backlog issue as the queue; the pull request
  with `Closes #n` and the verification ledger; ADRs with an "Amended by" line at the top,
  updated in the same pull request as the amendment; a checkpoint reduced to branch, head,
  claimed task and next action.
- **Owner gates.** File, Ready, Merge, as ADR 0003 defines them. The lifecycle workflow's
  G0 to G5 are renamed *phase gates* so the two vocabularies stop colliding.
- **Roles.** Owner, Planner, Implementer, Reviewer. A session holds one role and declares
  it in the claim comment. Mapping a role to a runtime unit (coordinator, thread, session,
  cloud task) is the adapter's job, not the core's.
- **Task boundaries.** `task-start #n`: refuse without `status:ready`, post the claim
  comment (runtime, reference, time), branch from `main`, write the claim with the task
  number and allowed paths. `task-finish [--stopped]`: run the verification contract on
  the exact head, write evidence naming the SHA, open the pull request with the ledger,
  update the checkpoint, post on the record, and append a proposals block for anything
  found mid-task. Conductor runs nothing between the two boundaries.
- **Verification contract.** Unchanged in shape: exact commands, cwd, expected result,
  evidence file. One rule added: evidence names the SHA it was run on, and a finish without
  matching evidence is a stopped finish.
- **Policy pin.** One file, `shared/WORKFLOW.md`, at a commit plus its SHA-256 digest,
  recorded in `.conductor/adoption.json` together with the list of generated adapters and
  the digest of each generated instruction text. The repository is not snapshotted into
  itself. The initializer verifies the pin; a session only reads the result.

### 3. The adapter contract

An adapter is generated per profile by the initializer from `shared/`, never hand-copied.
Each profile must supply:

1. the entry instruction file and where the runtime reads it;
2. the three always-on lines (project facts link, the session's role, and "Conductor runs
   at /task-start and /task-finish; never apply `status:ready`, never merge");
3. where the two boundary skills live for that runtime;
4. how the verification runner is invoked;
5. how the claim and the checkpoint are written;
6. the discovery check that confirms the runtime loaded the adapter;
7. an honest row in the capability matrix (section 6), marked observed, docs or unverified.

A profile ships as default data only when its row has been observed in a fresh session of
that runtime. Golden-output tests in the package check compare generated output with the
recorded expectation. A generated adapter is one instructions file plus a skills folder of
plain `SKILL.md` files; vendor extras are optional per-profile fields.

### 4. Four profiles

| Profile | Units | Generated | Rails in the session |
| --- | --- | --- | --- |
| `claude-code-projects` | coordinator = Planner; thread = Implementer; a thread asked for on a PR = Reviewer | project-instructions text from `PROJECT-INSTRUCTIONS.template.md` with its digest in `adoption.json`; repo `CLAUDE.md` with the three lines; owner checklist (enable the two account skills, pin the Backlog issue, set the repo variable, turn bypass off) | none; threads have no hooks |
| `claude-code` (standalone) | a local or single-repo cloud session holds one declared role; a scheduled task with a GitHub trigger can be the Reviewer | `CLAUDE.md`; `.claude/rules/*.md` with `paths:` globs; `.claude/skills/task-start` and `task-finish`; `.claude/settings.json` hooks | five hooks: session-start pin verify and context injection; deny merge, push to `main` and `status:ready`; allowed-paths gate on edits without a claim; stop check against evidence for HEAD; pre-compact checkpoint skeleton |
| `codex-cloud` | a cloud task started from the web or an `@codex` mention on a Ready issue is the Implementer; `@codex review` is an advisory Reviewer with its own bot identity | root `AGENTS.md` from the same source as `CLAUDE.md`; nested `AGENTS.md` where the Claude adapter has rules files; `.agents/skills/task-start` and `task-finish`; an environment setup script that verifies the pin | none; command hooks are not supported under cloud orchestration |
| `codex-local` | a CLI or IDE session on the owner's machine holds one declared role | the same `AGENTS.md` set as `codex-cloud`; `.agents/skills`; `.codex/hooks.json` carrying the same five rails as `claude-code`; `.codex/rules` for the command denies | hooks run only when the project's `.codex/` layer is trusted and `features.hooks` is on; the discovery check confirms both |

`CLAUDE.md` and `AGENTS.md` are generated from one template with one substitution: the
native skill folder and the hook file. Only `claude-code-projects` is in the MVP sprint;
the other three ship one per sprint, each after its spike (#45 to #49 and the Backlog
lines of the plan).

### 5. Enforcement and identity

Enforcement lives in GitHub and binds every runtime equally, including the ones that act
as the owner:

- branch protection on `main` with "Do not allow bypassing" on and "Require approvals"
  off (decided 2026-10-22 11:11 UTC; to be verified from a thread under #48);
- `linked-task` requiring `Closes #n`, exactly one priority and one category, and
  `status:ready` on #n (lands in the re-pin, #45);
- `verify`, with the pull-request ledger naming the tested SHA.

Session hooks, where a runtime has them, are guard rails and never the boundary. The
assistant's instructions never enforce.

Identity: Claude Code threads and sessions act as the owner on GitHub, and the App route
closed with #40 because the session proxy blocks the App API. Codex cloud brings a bot
identity for reviews and possibly for pull requests. The two are not made symmetrical.
The position from #37 stands: `status:ready` proves the owner's attention, the merge proves
the owner, approvals are off, so no gate depends on who authored a comment. A CI-minted App
token for reconciliation writes is a Backlog line, not part of this decision.

### 6. Capability matrix

What each runtime loads, as of 2026-10-22. **observed** means seen in a session of this
project (#41, the Planner session, this thread). **docs** means the vendor documentation
says so. **unverified** means a spike must confirm it before the adapter ships.

| Mechanism | Claude Code project thread | Claude Code standalone (cloud, one repo) | Claude Code local | Codex cloud task | Codex local (CLI, IDE) |
| --- | --- | --- | --- | --- | --- |
| Always-on repo instructions | `CLAUDE.md` (observed) | `CLAUDE.md` (observed) | `CLAUDE.md` (observed) | `AGENTS.md`, nested (docs) | `AGENTS.md` plus `~/.codex/AGENTS.md` (docs) |
| Always-on text outside Git | project instructions, 16,000 chars (observed) | none | `~/.claude/CLAUDE.md` | environment prompt (docs) | `~/.codex/AGENTS.md` |
| Procedure loaded by path | `.claude/rules` (unverified; #41 criterion 2 not observed) | `.claude/rules` (docs) | `.claude/rules` (docs) | nested `AGENTS.md` (docs) | nested `AGENTS.md` (docs) |
| Repository skills | `.claude/skills` **not loaded** (observed) | `.claude/skills` (docs) | `.claude/skills` (observed) | `.agents/skills` (unverified in cloud) | `.agents/skills` (docs) |
| Account or user skills | account skills (observed) | account skills (docs) | `~/.claude/skills` (observed) | unknown (unverified) | `~/.agents/skills` (docs) |
| Hooks (deny a tool call, inject context) | none (docs) | `.claude/settings.json` (docs) | `.claude/settings.json` (observed) | command hooks unsupported (docs) | `.codex/hooks.json` when `.codex` is trusted and `features.hooks` is on (docs) |
| Command permission rules | none | settings permissions (docs) | settings permissions (docs) | environment sandbox only (docs) | `.codex/rules/*.rules`, `config.toml` (docs) |
| GitHub identity for comments and PRs | owner (observed) | owner (observed) | owner, via `gh` | `chatgpt-codex-connector[bot]` for reviews; PR author unverified | owner, via `gh` |
| Started from GitHub | no, the coordinator starts it | scheduled task with GitHub trigger (docs) | no | `@codex` mention on an issue or PR (docs) | no |
| Branch protection and required checks bind it | yes, once bypass is off (observed off during #41) | yes | yes | yes | yes |

Two rows decide the design. Project threads and Codex cloud tasks have no hooks, so for
those two the only mechanical enforcement is GitHub's. Project threads load account skills,
so the boundary skills reach them once the owner enables them on the account, a one-time
owner step the repository cannot do.

## Alternatives considered

- Keep Projects parked and build the standalone adapter first, as decided at 11:07 UTC.
  Rejected by the owner at 12:11 and 12:56 UTC: the coordinator-plus-threads shape is the
  one the owner works in, and the gaps #41 found are closed by GitHub enforcement and
  account skills rather than by avoiding Projects.
- One hand-maintained kit per runtime, as before ADR 0002. Rejected: every new wrapper
  needed a copy per kit, and seven owed copies never arrived.
- Enforce roles and gates in the assistant's instructions or in hooks. Rejected on #37
  round 4: two of the four runtimes have no hooks, and instructions never block anything.
- A separate GitHub identity for Claude sessions as a precondition. Rejected with #40: the
  proxy blocks the App API; the gates were redesigned so that none depends on identity.
- Record the amendments only in comments and leave the ADRs as they are. Rejected: that is
  the problem this record fixes.

## Consequences

- New: this record; "Amended by: ADR 0004" lines under the Status of ADR 0002 and ADR 0003.
- Restated: ADR 0002's "one kit" is now "one core, generated adapters". The deletions of
  ADR 0002 stand; the Claude Code kit becomes the reference generated output.
- Superseded: the 11:07 UTC decision on #37 and #41. The standalone roles model it
  restored is now the `claude-code` profile, not the default.
- Follows from this record, each on its own record: the single re-pin (#45), the boundary
  skills (#46), the Projects profile in the generator (#47), the owner setup verified from
  a thread (#48), the pilot task (#49); then the standalone hooks, the Codex local and
  Codex cloud spikes and profiles, as Backlog lines.
- Unchanged by this record: `shared/WORKFLOW.md` and its pinned digest, the initializer,
  every generated adapter, the verification contract, the gates and roles of ADR 0003.

## Rollback

Delete this record, remove the two "Amended by" lines, and regenerate `MANIFEST.json`.
The decisions then revert to ADR 0002 and ADR 0003 as merged, plus the comment amendments
on #36 and #37, including the 11:07 UTC parking of Projects. No generated file depends on
this record.
