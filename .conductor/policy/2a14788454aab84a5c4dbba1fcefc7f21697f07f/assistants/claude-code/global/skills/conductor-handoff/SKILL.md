# Conductor handoff

1. Read the active project instructions and their pinned shared-practice file. Verify the
   binding before dependent work. Locate the project's checkpoint destination from those
   instructions; if missing, ask for the destination while gathering read-only evidence.
2. Inspect current repository identity, branch/HEAD, working-tree changes, and relevant
   evidence. Preserve existing checkpoint content that remains useful. Do not invent a
   project path, owner, command, remote issue, or completed action.
3. Write or update only the authorized project-local checkpoint. Use this compact structure:

   - Objective and acceptance criteria.
   - Current owner, environment, repository, branch, base/HEAD, and uncommitted file list.
   - Shared-practice path, source identity and verified digest.
   - Completed work and decisions, with file/artifact references.
   - Verification commands, working directories, results, and unrun checks.
   - Analytics provenance and reproduction evidence when applicable.
   - Blockers, unresolved questions, next action, and any proposed owner transition.
   - Publication state: local changes, remote updates, and deployment, each evidenced.

4. Record necessary task facts only; omit secrets and private conversation transcripts.
   Follow the loaded shared policy for authorization and coordination. Do not treat labels
   or an owner note as an exclusive lock. Do not post GitHub progress without supported
   access and destination-specific authorization; leave a local draft if needed.
5. When resuming, compare the checkpoint with current files and revisions. Report stale or
   conflicting facts before relying on them. Reconcile them from evidence, preserve the
   fixed policy binding, and continue the authorized next action.
6. Report the checkpoint path, what is complete, what remains, and whether anything was
   actually published. If the checkpoint could not be saved, provide the draft and blocker.
